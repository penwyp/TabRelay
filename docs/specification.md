TabRelay 是一个基于 Chrome Manifest V3 和 WebDAV 的多设备浏览器工作区接力工具。它自动采集并同步本机所有普通浏览器窗口、标签及当前已打开的标签组。用户从设备列表中主动选择另一台设备的快照并恢复时，TabRelay 保留本机已有窗口和标签，以新增窗口的方式导入来源内容，然后将恢复后的完整本机状态上传到 WebDAV。

**核心语义：设备独立发布、按需读取、非破坏性合并恢复、合并后自动回传。** 远端设备不会因为本机恢复操作被修改，也不会在未获用户主动选择时自动打开其他设备的标签。

# 产品范围

**V1 支持：**

- 自动同步本机所有普通窗口，不要求用户逐个选择同步窗口。

- 保存每个窗口的标签顺序、URL、标题、置顶状态，以及当前打开的标签组名称、颜色、折叠状态和成员关系。

- 每个浏览器 Profile 中的插件安装实例自动生成独立 UUID，提供可修改的设备显示名称。

- 在插件侧边栏查看所有设备的最后同步时间、窗口数、标签数与快照详情。

- 支持恢复其他设备的全部窗口、指定窗口、指定标签组或标签；默认以新窗口追加，绝不关闭或覆盖本机原有窗口。

- 恢复完成后自动采集本机所有窗口，并发布新的设备快照。

- 保留上一次有效非空恢复点和有限历史快照，支持同步失败重试及恢复进度查看。

**V1 非目标：** 自动将远端标签实时打开到所有设备、跨设备协同编辑同一组标签、同步登录状态和页面内存、恢复未打开的浏览器“已保存标签组”。

# 合并语义与示例

假设设备 A 有 2 个窗口、30 个标签；设备 B 有 3 个窗口、20 个标签。

1. A 自动上传快照 A-17；B 自动上传快照 B-42。

2. B 在设备列表选择 A，点击“恢复全部窗口”。

3. TabRelay 在 B 上新增 2 个窗口，按 A 的快照重建标签和标签组；B 原有 3 个窗口保持不变。

4. 完成后 B 共拥有 5 个窗口、约 50 个标签（去除被安全策略过滤的标签，且可能按溯源规则跳过重复导入项）。

5. B 上传新快照 B-43；A 仍然拥有原来的 2 个窗口，其 A-17 不受影响。

因此，WebDAV 同时保存 A-17 与 B-43。其他设备既能选择 A 的原始工作区，也能选择 B 合并后的工作区。

这里的“合并”是 **在目标设备新增窗口并持久化结果**，不是在 WebDAV 上对所有设备构建一个随时自动收敛的全局标签集合。后者需要另行定义关闭标签的删除传播、冲突和所有权语义，否则会出现“我刚关掉的标签又被另一台电脑同步回来”。

~~~mermaid
sequenceDiagram
  participant A as 设备 A
  participant D as WebDAV
  participant B as 设备 B
  A->>D: 发布 A 当前快照
  B->>D: 发布 B 当前快照
  B->>D: 读取 A 的指定快照
  B->>B: 保留原窗口，新增 A 的窗口副本
  B->>D: 发布 B 的合并后快照
  Note over A,B: A 不变；B 的合并结果可供其他设备选择恢复
~~~

# 设备身份与数据存储

第一次启用时使用 `crypto.randomUUID()` 生成 `deviceId`，写入 `chrome.storage.local`；后续浏览器启动沿用。它标识的是一个浏览器 Profile 的插件实例，而非主板、网卡等物理硬件。同一电脑的不同 Chrome Profile 应视为不同设备。重新安装或复制 Profile 可能导致新 ID 或 ID 冲突；遇到远端同 ID 的并发写入时暂停发布并引导重新生成实例 ID。

WebDAV 使用每个设备独立目录，不使用多设备共同写入的全局 `current.json`：

~~~text
tabrelay/v1/
  devices/
    <device-id-A>/
      device.json
      current.json
      recovery.json
      history/
    <device-id-B>/
      device.json
      current.json
      recovery.json
      history/
~~~

- `device.json`：设备 ID、显示名称、客户端版本、最后成功发布时间。

- `current.json`：最新完整状态，可以表示空工作区。

- `recovery.json`：最近一次成功保存的有效非空工作区。

- `history/`：保留最近若干恢复点，默认建议 20 个，可配置清理。

设备列表通过 WebDAV `PROPFIND Depth: 1` 枚举目录；不要维护由所有设备共同修改的中央索引文件。

# 快照数据模型

一个快照是某台设备在特定时刻的全部普通窗口状态，而不是浏览历史流水。

~~~json
{
  "schemaVersion": 1,
  "deviceId": "device-B",
  "snapshotId": "snap-43",
  "revision": 43,
  "capturedAt": "2026-11-01T10:00:00Z",
  "windows": [
    {
      "windowKey": "win-B-01",
      "order": 0,
      "activeTabKey": "tab-B-07",
      "groups": [
        {
          "groupKey": "group-B-03",
          "title": "Research",
          "color": "blue",
          "collapsed": false
        }
      ],
      "tabs": [
        {
          "tabKey": "tab-B-07",
          "url": "https://example.org/article",
          "title": "Example",
          "index": 0,
          "pinned": false,
          "groupKey": "group-B-03",
          "origin": {
            "deviceId": "device-A",
            "tabKey": "tab-A-19"
          }
        }
      ]
    }
  ]
}
~~~

`windowKey`、`groupKey` 和 `tabKey` 是扩展维护的逻辑标识，不能把 Chrome 运行时的 `windowId`、`tabId`、`groupId` 直接当作跨设备永久 ID。窗口顺序只用于快照显示；恢复时由新窗口重新分配运行时 ID。浏览器重启后对逻辑标识进行尽力重关联，存在完全相同 URL 和位置时不保证无歧义。

# 全窗口采集与自动同步

采集器通过 `chrome.windows.getAll({populate:true})` 获取窗口，明确过滤为普通窗口并排除无痕窗口；使用 `chrome.tabGroups.query({})` 读取当前打开的标签组。根据窗口、组与标签关系生成一致的完整快照。

监听 `tabs.onCreated`、`onUpdated`、`onRemoved`、`onMoved`、`onAttached`、`onDetached`，以及 `windows`、`tabGroups` 的相关事件。事件只表示工作区“变脏”，实际采集以一次完整查询为准，避免尝试通过事件顺序拼接最终状态。

建议的发布过程：

1. 事件到来后立即把 `dirty` 与待同步版本写入持久化存储。

2. 短暂防抖（建议 3 秒），采集全部当前窗口，过滤无效记录，写本地待发布快照。

3. 对快照计算内容哈希；内容未变化时跳过不必要的上传。

4. 先 `PUT` 临时文件，再尽可能使用 WebDAV `MOVE` 发布，并校验远端内容；使用 ETag 或版本机制发现同设备意外多写者。

5. 成功后推进 `revision`，记录最后成功时间；失败时持久化待上传快照并重试。

6. 使用 `chrome.alarms` 定期兜底，不能假设 MV3 Service Worker 永久驻留。

浏览器启动阶段等待标签会话恢复基本稳定后再发布；关闭最后一个窗口或采集为空时允许 `current` 为空，但不得覆盖 `recovery` 中的最后有效非空工作区。最后窗口关闭时不保证异步上传一定完成，应保留已经持久化的最近版本。

# 新窗口合并恢复流程

用户在侧边栏选择来源设备与快照，可勾选全部窗口、部分窗口、标签组或单个标签。默认恢复模式为“新窗口追加”。

**阶段 1：预检（不修改浏览器）。**

- 从 WebDAV 读取所选快照并固定 `snapshotId`、`revision` 与内容哈希；后续恢复使用这份固定内容。

- 校验协议版本、设备 ID、时间、JSON 结构、数组上限、URL 格式、组引用和数据大小。

- 按安全规则过滤不允许打开的 URL；显示“计划新增 N 个窗口、M 个标签、G 个标签组，跳过 K 个”。

- 预先展示本机现有窗口数；用户确认后才开始更改浏览器。

**阶段 2：建立持久化恢复任务。** 生成 `restoreOperationId`，记录来源快照、选中项、进度、已创建窗口和标签 ID，状态设为 `PREPARED`。恢复任务串行执行，避免两次快速点击交错创建重复窗口。

**阶段 3：创建窗口与标签。** 若选择来源设备的全部 3 个窗口，则在本机新增 3 个普通窗口；若只选择一个标签组，则新增 1 个窗口。每个窗口先用第一个安全 URL 执行 `chrome.windows.create({url, focused:false})`，再调用 `chrome.tabs.create({windowId, url, active:false})` 添加剩余标签，防止留下多余空白标签。按快照顺序创建并记录实际 tabId。

**阶段 4：重建组结构。** 对同一逻辑组下的标签执行 `chrome.tabs.group({tabIds, createProperties:{windowId}})`，再用 `chrome.tabGroups.update(groupId,{title,color,collapsed})` 恢复名称和颜色；最后核对标签顺序、置顶状态以及活动标签。原始组 ID 不跨设备复用。

**阶段 5：核验与提交。** 对新窗口读取实际标签列表，记录成功、失败与跳过项。恢复完成后标记本机工作区为 Dirty，重新采集 **本机全部窗口**（包括恢复过程中用户手动修改的窗口），发布为本机新快照。不要把“恢复开始前采集的本机 JSON”和远端 JSON 简单拼接后反写浏览器或 WebDAV，因为这样可能复活用户在恢复过程中已经关闭的标签。

**阶段 6：反馈。** UI 显示新增窗口数、成功标签数、跳过原因以及“合并结果已同步 / 等待同步”。浏览器恢复成功但 WebDAV 上传失败时，显示“本机已恢复，远端待同步”，不能误报完全成功。

# 去重、来源溯源与回环控制

“合并”不等于简单用 URL 建立集合。同一个 URL 可以故意在两个窗口或不同标签组中出现，因此不能默认全局按 URL 去重。

采用两层策略：

1. **恢复任务级去重**：同一 `restoreOperationId` 在任务进行中不得重复执行；记录每个已创建标签的操作进度。进程重启后先检查已创建窗口和本地恢复日志，再决定恢复剩余部分。

2. **标签来源级去重**：原始标签分配 `origin.deviceId + origin.tabKey`；恢复副本继续携带这组来源标识，同时获得自己的本地 `tabKey`。再次从其他设备恢复时，如果本机已存在同来源且同内容的标签，默认提示或跳过，避免 A→B→A 的回环复制。

相同 URL 但不同来源的标签默认保留；UI 可以提供“额外按 URL 去重”选项，但不设为默认。

由于浏览器 API 不能提供跨所有重启和跨浏览器实例永不变化的标签主键，完全精确的跨重启去重并无保证。插件应持久化来源关系、恢复日志，并在无法确认时向用户展示疑似重复项，而不是擅自删除。

# 恢复事务、失败与回滚

浏览器没有“批量创建多个窗口及分组的原子事务”能力，因此采用可恢复的任务日志，而不是声称严格一次性提交。

| 场景 | 处理语义 |
| --- | --- |
| 同步时 WebDAV 断网 | 保留本地待上传快照，恢复网络后重试 |
| 远端快照损坏 | 预检失败，不创建任何窗口 |
| 某个 URL 无法打开 | 记录单项失败，继续恢复其他安全标签 |
| 恢复创建到一半扩展被终止 | 从日志和实际窗口核对后，提示继续或保留当前结果 |
| 用户在恢复期间点击取消 | 停止创建后续标签，已创建窗口默认保留 |
| 用户要求撤销本次恢复 | 仅在明确确认且可核实目标窗口仍归该任务管理时关闭这些新增窗口；绝不触碰恢复前原有窗口 |
| 合并后远端发布失败 | 本机恢复已完成，继续后台重试同步 |
| 来源设备此时更新了快照 | 本次继续使用确认时固定的版本，不中途切换 |

恢复中不应关闭所有自动采集事件，只需延迟发布中间态。任务完成时统一生成最终状态；如果恢复被中断，仍应允许把实际存在的部分工作区保存下来。

# 安全与隐私边界

1. **远端数据不可执行。** WebDAV 返回的快照、网页标题和组名一律视为不可信数据。UI 使用安全文本渲染，禁止将标题或 URL 拼成 `innerHTML`，更不能通过脚本注入来“恢复”页面状态。

2. **限制可恢复的 URL。** 默认只允许绝对 `http:` 和 `https:` URL。拒绝 `javascript:`、`data:`、`blob:`、`chrome:`、其他扩展页面和未明确授权的 `file:` 路径；不要用 `scripting.executeScript` 绕过这些限制。

3. **排除私密上下文。** 默认不采集无痕窗口；支持用户定义域名黑名单、URL 查询参数敏感信息处理规则。某些登录令牌可能出现在 URL 中，上传前必须告知该风险。

4. **最小权限。** 使用 `tabs`、`tabGroups`、`storage`、`alarms` 与必要的 WebDAV 主机权限；不需要网页内容脚本、Cookie 权限或浏览历史权限。

5. **凭据隔离。** 强制 HTTPS 与 WebDAV 应用专用密码，禁止在日志及分享快照中输出凭据。把敏感配置限定在扩展受信任上下文，禁止不受信任的快照决定凭据发送的目标地址。

6. **服务端保密。** 建议使用客户端 AES-GCM 加密 URL、标题及结构快照，设备名称和最近同步时间可以单独保留明文用于设备列表。为了无人值守同步，解锁后的密钥需要安全保存在本地或受本机密钥保护；这解决 WebDAV 服务端泄露风险，但不能承诺抵御已攻陷的本地浏览器。

7. **限制资源放大。** 设置单次恢复的窗口数、标签数、快照大小的默认安全阈值。大批量创建应分批执行，并提示内存和登录压力；不允许畸形快照无限量创建标签。

8. **浏览器能力边界。** 只恢复可访问 URL、当前已打开标签组的结构及有限标签属性；不承诺恢复 Cookie、表单内容、页面滚动、Back/Forward 历史、网页内存状态或未打开的已保存标签组。

# 工程实现模块

建议使用 TypeScript + Manifest V3；侧边栏作为主要操作界面，工具栏 Popup 只显示同步状态和打开侧边栏的入口。

| 模块 | 职责 |
| --- | --- |
| DeviceRegistry | 生成与维护本机设备 ID、显示名称和同 ID 冲突检测 |
| SnapshotCollector | 全窗口采集、组关联、逻辑 ID 映射与安全过滤 |
| WebDAVRepository | PROPFIND、GET、PUT、MOVE、ETag 校验、重试及目录管理 |
| SyncCoordinator | Dirty 状态、事件防抖、待上传队列、周期性兜底 |
| RestorePlanner | 预检来源快照、用户选择、URL 过滤、去重与恢复计划 |
| RestoreExecutor | 新窗口创建、标签组重建、任务进度、取消及失败续做 |
| RecoveryJournal | 持久化恢复操作、创建映射和异常恢复 |
| SidePanel UI | 设备列表、窗口与组预览、选择恢复、同步错误反馈 |

Chrome 提供 `windows.create`、`tabs.create`、`tabs.group`、`tabGroups.update` 等所需接口。依靠 Service Worker 的内存变量保存恢复进度是不可靠的，任务状态必须持久化。

# 验收标准

- [ ] A、B 两个设备的所有普通窗口自动分别发布，互不覆盖。

- [ ] B 恢复 A 的全部窗口，B 原窗口数量与内容不变；新增窗口准确重建标签组及标签顺序。

- [ ] B 恢复完成后生成新快照，另一台设备能够看到 B 的合并结果。

- [ ] A 的快照与浏览器窗口不因 B 的恢复动作而变化。

- [ ] 再次恢复同一来源快照时，重复来源提示或跳过，不会无提示形成无限回环复制。

- [ ] 断网、WebDAV 401/403、超时与冲突均有明确状态与可重试路径。

- [ ] 浏览器重启、扩展 Service Worker 中断、恢复到一半失败均不会破坏原有窗口。

- [ ] 空窗口状态与浏览器关闭不会覆盖最近有效的非空恢复点。

- [ ] 远端快照中的危险协议 URL、畸形结构、超限数据不会被执行或无限创建。

- [ ] 恢复中用户主动关闭或修改原有标签，最终同步以浏览器真实当前状态为准。

**V1 交付边界：** 以设备为单位自动发布全部窗口；以用户主动选择为触发完成非破坏性新窗口恢复；恢复后的本机合并状态自动回传。这样既实现跨电脑接力，也避免全自动多主合并所带来的删除冲突。
